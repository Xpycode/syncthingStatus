# Session 2026-08-10 — 🚀 v1.6.1 released; sandboxed-updater root cause found & fixed

## TL;DR
v1.6.1 (build 163) cut, notarized, published, appcast live — from the **M4-Pro** (first release
from this Mac). While cutting it, the user's own failed 1.5.5→1.6.0 update exposed the real story:
**every sandboxed release ever shipped could download updates but never install them.** Fixed in
1.6.1 and proven end-to-end with a live local-feed update test before the DMG was even signed off.

  the vault README's 2026-07-27 audit had already flagged that staleness).

- User believes the key is also in Strongbox but unlabeled — registry notes the retitle task.
- The Keychain here has five OTHER apps' Sparkle keys (per-app accounts); no syncthingStatus one —
  `sign_update -f <file>` signs straight from the vault file, no import needed.

## Root cause of "download finished, then update error" (user's own 1.5.5)
Unified log caught the user's 18:36 attempt (`log` is a **zsh builtin** — two silent empty scans
until `/usr/bin/log` was used):

```
[Sparkle] Failed copying system domain rights: -60005
[Sparkle] Failed to submit installer job
[Sparkle] If your application is sandboxed please follow steps at: …/sandboxing/
[Sparkle] Error: An error occurred while launching the installer.
```

The App Sandbox went on in the 1.5.x era, but Sparkle's sandbox accommodations were never added —
so Sparkle fell back to Authorization Services, which the sandbox denies. **Not** a key/signature
problem: v1.6.0's published appcast signature verified VALID against Group B (pure-Python Ed25519
verifier, `scratchpad/verify_ed25519.py` pattern), length matched byte-for-byte, and 1.5.5's
nested Sparkle binaries are all correctly Dev-ID signed.

**Fix (`a0eebbd`), per sparkle-project.org/documentation/sandboxing/:**
- Info.plist: `SUEnableInstallerLauncherService` = YES
- entitlements: `com.apple.security.temporary-exception.mach-lookup.global-name` =
  [`$(PRODUCT_BUNDLE_IDENTIFIER)-spks`, `-spki`]
- Downloader XPC service deliberately NOT enabled (app has `network.client`; docs warn against it)

Old installs are unfixable remotely (the broken installer is in the *installed* app) → README +
appcast + GitHub release all tell ≤1.6.0 users: **one manual download**, then updates work forever.

## Gotchas recorded
- `log` in zsh is a **builtin** — `log show`/`log stream` silently do nothing in `zsh -c`; use
  `/usr/bin/log`. Cost this session two empty 30-day scans.
- `codesign -d` on the post-staple export path returned "host has no guest with the requested
  attributes" (macOS 27 beta quirk?) — same bits read fine from the mounted DMG.
- Version compare traps for the appcast: `sparkle:version` is the BUILD number (163), not 1.6.1.
