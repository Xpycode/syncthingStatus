# Session: 2026-08-09

## Goal
Diagnose and fix a user-reported connection failure — "failed to connect to Syncthing: The
certificate for this server is Invalid. You might be connecting to a server that is pretending to
be…" — reported without a version number.

## Progress

**Root cause: no TLS trust handling anywhere in the app.** `SyncthingClient.init` built a plain
`URLSession(configuration:)` with no delegate, and a project-wide grep for `URLSessionDelegate` /
`URLAuthenticationChallenge` / `SecTrust` returned nothing — so **every released version is
affected**, 1.5.x and 1.6.0 alike. The reporter's version question was a dead end.

Syncthing's `<gui tls="true">` ("Use HTTPS for GUI") serves the REST API with a self-signed cert
from `https-cert.pem`, and — confirmed from Syncthing's config docs — **also redirects plain HTTP to
HTTPS**. So the failure reaches users who never touched the default `http://127.0.0.1:8384` base
URL. TLS fails before the API key is sent, which is why their correct key made no difference.

**Fix** (`Client.swift`, commit `68e927f`):
- New `SyncthingServerTrustDelegate` — grants trust only when the challenge host is loopback
  (`localhost`, `::1`, anything in `127.0.0.0/8`); everything else gets `.performDefaultHandling`.
- Session built with that delegate; the injected-session path used by tests is untouched.
- `fetchStatus`'s `URLError` switch gained the `serverCertificate*` cases, so remote failures name
  the "Use HTTPS for GUI" setting instead of showing Apple's "pretending to be" wording.

**Verification** — built green (ad-hoc, no dev cert on this Mac), then the delegate was extracted
verbatim and run against a real self-signed HTTPS server:

| Scenario | Result |
|---|---|
| `https://127.0.0.1:8385`, delegate on | OK |
| `https://localhost:8385`, delegate on | OK |
| `https://127.0.0.1:8385`, delegate **off** | FAILED −1202 — reproduces the user's error verbatim |
| `https://<LAN IP>:8385`, delegate on | FAILED −1202 — correctly refused |
| `http://…:8386` → 301 → `https://…` | OK — the likely real-world user path |

Plus 13 `isLoopback` unit checks including the spoof attempts `127.0.0.1.evil.com` and
`127.0.0.256`. The delegate-off row is the important one: it reproduces the reported failure
exactly, so the diagnosis is demonstrated rather than asserted.

## Decisions
- **Self-signed certs trusted on loopback only** — full entry in `decisions.md` (2026-08-09).
  Auto-trust is safe precisely and only where there is no network for an impostor to sit on;
  a self-signed cert from a *remote* host is indistinguishable from a real interception, so those
  stay a hard failure. Remote-HTTPS users (NAS, another machine) are **unsupported by design** —
  the opt-in TOFU-pinning option is the follow-up if more reports arrive.
- Rejected: blanket cert acceptance (real MITM hole for remote users), and error-message-only
  (would tell every HTTPS user to switch HTTPS off rather than supporting them).
